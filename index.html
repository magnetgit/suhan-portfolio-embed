완료 · 회원과 데이터 구조

  • 비밀번호 해시를 가입·로그인·찾기·탈퇴에 적용하고, 기존 평문 계정은 첫 로그인 때 해시로 바꾸도록 했습니다. 아이디·이메일을 분리하고 성별·나이대는 동의한 경우에만 저장합니다.
  • 모델을 Django 마이그레이션 관리로 바꾸고 예산·리뷰·도움돼요 테이블과 관리자 화면을 정비했습니다. 로컬·서버 모두 MariaDB를 쓰도록 설정을 정리했습니다. 직접 작성
  • 외부 API 결과 캐시를 DB 테이블에 저장해, 카카오 대중교통 경로처럼 반복되는 결과를 서버를 다시 시작해도 재사용합니다.
  • 여행 표에 인원 칸을 추가해(마이그레이션) 계산 인원을 로그인 세션 대신 DB에 저장합니다.
  • 여행 상세·수정·삭제와 일정 편집에 로그인·작성자 확인과 입력 검사를 넣어 다른 회원의 여행을 보거나 바꿀 수 없게 하고, 서버 로그에서 API 키를 가렸습니다.
  • 채팅·여행 만들기·인증번호 요청에 횟수 제한을 두고, 로그인 없이 외부 API를 부를 수 있던 주소를 막았습니다.

완료 · 리뷰 기반 맞춤 추천

  • 리뷰 목록 API와 여러 장소의 평균 별점·리뷰 수를 한 번에 돌려주는 요약 API를 만들었습니다.
  • 최신 리뷰를 LLM으로 읽어 장소별 키워드와 한 줄 요약을 만들고, 저장해 두었다가 리뷰 수가 바뀔 때만 다시 요약합니다. 직접 작성
  • 채팅 추천 카드 순서에 같은 성별·나이대 회원의 리뷰 평점을 섞고, 여행 컨셉과 리뷰 키워드가 겹치면 가산점을 줍니다.
  • 리뷰·관광지 검색(RAG)용 임베딩 테이블과 생성·저장·유사도 검색 함수를 만들어 팀 공통 함수로 공유했습니다. 직접 작성 이를 이용해 리뷰가 비슷한 장소를 찾는 API도 만들었습니다.
  • 리뷰 게시판에 장소·카테고리·지역·태그·나이대·성별 분류 보기와 추천순·최신순·별점순 정렬, 번호 페이지를 넣었습니다.
  • 리뷰 키워드 요약을 GPT와 로컬 공개 모델(qwen3·EXAONE·Llama)로 같은 조건에서 비교하고, 결과로 프롬프트를 보완했습니다.

완료 · 일정과 이동

  • 채팅에서 담은 장소가 숙소 도착 뒤에 붙거나 다른 날에 중복되던 문제를 고쳐, 숙소 앞에 넣고 순서·시간을 다시 계산합니다. 직접 작성
  • 담은 장소를 운영시간 안에 넣고 점심(12~13시)·저녁(18~19시) 시간대를 지키도록 체류 시간을 조절합니다. 대중교통 구간은 카카오 경로 시간을 씁니다.
  • 여행지까지 가는 방법(KTX·고속버스·항공·배·자차)을 공공데이터 시간표로 비교하고, 고르면 첫날 일정·지도·교통 예산에 반영합니다. 가는 길은 첫날·마지막 날에만 접어서 보여 줍니다.
  • 섬 여행은 항구마다 대중교통+배, 항구에 차 두고 배, 차 싣는 배를 비교하고 운항 시간표에 없는 노선은 뺍니다. 뱃삯은 어림값으로 안내합니다.
  • 차로 2시간 넘는 구간에는 휴게소를 넣고(최대 3곳), 지방 소도시 139곳의 가는 길을 추가했습니다. 지난 날짜로는 일정을 만들 수 없게 했습니다.
  • 채팅의 “○○ 근처 숙소”를 일정에 담아 둔 장소 기준으로 찾게 고치고, 추천 숙소를 지도에 번호 점과 가격 카드로 겹치지 않게 표시합니다.
  • 축제 예상 요금(1인 요금 × 인원)과 연박 숙박비 한 번 계산을 넣고, 예산 금액 변경을 DB 트리거로 자동 기록해 조회 API로 보여 줍니다.

완료 · AI 구성과 화면

  • 채팅 에이전트(LLM·도구 호출·추천 카드)를 FastAPI 서버 프로세스로 분리했습니다. 응답 모양은 그대로 두고, 설정 한 줄로 예전 방식과 바꿀 수 있으며 토큰 검사를 넣었습니다.
  • 관광지 소개글 RAG에서 다른 도시의 같은 이름 장소가 붙던 문제를 좌표 20km 기준으로 고치고, 잘못 들어간 데이터를 정리하는 명령을 추가했습니다.
  • 화면 언어 바꾸기(한국어·영어·일본어·중국어)를 넣었습니다. 미들웨어가 모든 화면에 사전을 붙이고, 사전에 없는 글은 LLM 번역을 DB에 저장해 다시 씁니다(요청 횟수·길이 제한).
  • 채팅에서 날짜·인원·숙소·예산·가는 방법을 한 문장에 말해도 날짜를 코드로 해석해 한 번에 채우도록 고치고, 서버에서 여러 문장으로 확인했습니다.
  • 폰 화면을 보완했습니다(기기 12종 미리보기, 안전 영역, 버튼 글자 한 줄 맞춤, 아이폰 확대를 막는 16px 입력 칸, 404·500 화면). PC/폰 전환 버튼을 모든 화면에 붙이고, 2박 이상 숙소 고르기와 일정 끌어 놓기 버그도 고쳤습니다.
  • 비밀번호 찾기를 아이디 → 이메일 → 이름 → 인증 코드(6칸·다시 받기·남은 시간) 단계 화면으로 바꾸고, 비밀번호 규칙을 영문 대·소문자+숫자로 완화했습니다.
  • Streamlit 운영 대시보드로 회원·여행·리뷰·예산 변경의 월별·연도별 증감, 선호 장소, 장소별 비용을 보여 줍니다. 직접 작성

완료 · AWS 서버 운영

EC2에 Nginx → Gunicorn → Django와 MariaDB를 구성하고 HTTPS 인증서·요금 알림을 설정했습니다. 테이블 이름 대소문자 차이로 저장이 실패하던 문제는 소문자 통일로 해결했고, 서버를 운영 설정으로 전환했습니다.

11월 19일 기준 팀 main 변경(PR #177)까지 서버에 배포하고 응답을 확인했습니다. nginx에 글자 파일 압축(gzip)과 정적 파일 10분 캐시를 설정해 스타일 파일을 160KB에서 32KB로 줄였습니다. 배포 스크립트가 사이트·운영 대시보드(비밀번호 보호)·AI 서버를 함께 다시 시작해 확인하고, 배포 직전과 매일 DB를 백업합니다(14일 보관). 관광지 소개글 데이터는 API 하루 사용량에 맞춰 밤마다 나눠 넣었고, 다 넣은 뒤 예약을 해제했습니다.

완료 · 비밀번호 찾기와 시연 데이터

이메일 인증 코드(6자리, 10분, 5회 제한)로 비밀번호를 찾는 서버 쪽을 만들고, 서버 전용 메일 계정으로 실제 발송을 확인했습니다. 시연용 데모 회원·여행·리뷰 데이터는 2020년부터, 여행지 15곳과 여러 출발지·이동 방법으로 넓혀 서버에도 적용했습니다.

관리 방식

브랜치와 PR

  • 역할별 브랜치(프론트 front · 백엔드 back · AI ai)에서 작업하고, main에는 PR로만 합칩니다.
  • PR 병합(대부분)과 서버 배포는 제가 맡았습니다. 충돌은 양쪽 내용을 살려 합치고, 같은 함수를 고친 PR은 하나로 묶어 병합했습니다.
  • 평일 마무리 시각에 제 작업 브랜치를 자동으로 push해 작업이 로컬에만 남지 않게 했습니다.

합의 규칙

  • 기존 응답 키와 함수 이름은 바꾸지 않고 추가만 합니다. 바꿔야 하면 세 사람이 합의합니다.
  • 여러 사람이 같이 쓸 함수·응답 키는 먼저 만드는 사람이 이름과 모양을 정해 문서에 먼저 올리고, 다른 사람은 그 정의를 그대로 씁니다.
  • 응답 키 기준은 mock.json, 화면 모양 기준은 목업 하나로 정했습니다.

기록과 공유

  • docs/TEAM_UPDATES.md에 변경·결정을 최신순으로 남기고, 항목마다 “다른 파트가 확인할 것”을 적었습니다(약 3,500줄).
  • pull 받은 뒤 내 파트에 영향이 있는지 보는 체크리스트(PULL_CHECKLIST.md)를 두었습니다.
  • main 병합 기준 팀 진행도 페이지, 날마다 팀 마무리 페이지와 개발 일지를 갱신했습니다.

개인 게임 프로젝트의 규칙과 구현

01. 어떻게 진행하나요?

  1. Enter로 시작

    약 2초의 라운드 준비 화면 후 시작합니다. 각 라운드의 제한시간은 10초로 다시 설정됩니다.

  2. 왼쪽부터 차례로 입력

    무작위로 만들어진 3~8개의 화살표를 WASD 또는 방향키로 입력합니다. W=↑, A=←, S=↓, D=→입니다.

  3. 완성하면 점수와 시간 획득

    한 문제를 모두 맞히면 점수를 얻고 시간이 1초 늘어납니다. 남은 시간은 최대 10초이며, 다음 문제로 바로 넘어갑니다.

  4. 실수하면 같은 문제를 처음부터

    틀린 입력은 현재 문제의 입력 위치를 초기화합니다. 직접적인 점수 차감이나 추가 시간 차감은 없지만, 타이머는 계속 흐르고 해당 라운드의 완벽 보너스를 잃습니다.

  5. 라운드를 클리어하며 계속 도전

    1라운드는 6문제, 2라운드는 7문제처럼 라운드마다 1문제씩 늘어납니다(라운드 번호 + 5). 결과 화면을 약 3초간 보여준 뒤 다음 준비 화면으로 넘어갑니다. 시간이 0이 되면 게임이 끝납니다.

02. 화면에는 무엇을 보여주나요?

  • 왼쪽 위: 현재 라운드 번호
  • 오른쪽 위: 지금까지 누적한 점수
  • 가운데: 현재 문제의 화살표. 입력 전은 흰색, 맞힌 화살표는 초록색으로 표시합니다.
  • 오답 피드백: 화살표 전체가 빨갛게 변하며 좌우로 흔들린 뒤 흰색으로 돌아옵니다. 입력·정답·오답에는 효과음도 재생됩니다.
  • 아래: 소수점 한 자리의 남은 시간과 시간 막대. 2초 이하가 되면 시간·막대·점수·라운드를 빨간색으로 바꿔 경고합니다.

03. 점수는 어떻게 계산하나요?

문제 점수는 완성 즉시 누적하고, 라운드를 성공했을 때만 세 가지 보너스를 더합니다.

항목계산 규칙적용 시점
문제 점수완성한 문제의 화살표 개수 × 5점
3개는 15점, 8개는 40점		문제 전체 완성 시
라운드 보너스현재 라운드 번호 × 25점라운드 클리어 시
시간 보너스남은 시간 × 10의 소수점 이하 버림
코드: int(time_left * 10)		마지막 문제의 +1초 반영 후
완벽 보너스해당 라운드에서 오답이 없으면 100점, 있으면 0점라운드 클리어 시
계산 예시 · 1라운드

6문제의 화살표 수가 3·4·5·6·7·8개라면 문제 점수는 33 × 5 = 165점입니다. 마지막 문제의 시간 회복까지 반영한 내부 남은 시간이 정확히 6.5초이고 오답이 없었다면:

165 + 25 + 65 + 100 = 355점

결과 화면에는 문제 점수, 라운드 보너스, 시간 보너스, 완벽 보너스, 총 획득, 누적 점수를 차례로 표시합니다. 이미 누적한 문제 점수를 다시 더하지는 않습니다.

시간 보너스는 화면에서 반올림해 표시한 숫자가 아니라 내부 시간값으로 계산합니다. 시간 초과 시에는 완성한 문제의 점수는 유지되지만, 실패한 라운드의 보너스와 미완성 문제 점수는 받지 못합니다.

04. 게임 종료와 랭킹

최종 점수를 약 3초간 보여준 뒤, A~Z로 최대 3글자의 이니셜을 입력합니다. Backspace로 지우고 Enter로 저장합니다. 빈 이름은 ‘-’로 기록합니다.

랭킹은 점수 높은 순 → 도달 라운드 높은 순 → 먼저 기록한 순으로 정렬해 JSON 파일에 최대 100건을 보관합니다. 화면에는 순위·이니셜·도달 라운드·점수를 표시하고, 상위 5위 밖의 플레이어 기록은 별도 줄로 보여주도록 구성했습니다. Enter를 누르면 시작 화면으로 돌아갑니다.

05. 구현하며 배운 것

게임 상태를 타이틀·준비·플레이·결과·이니셜·랭킹으로 나누고, 상태에 따라 키 입력을 처리했습니다. Tkinter의 예약 콜백으로 타이머와 화면 전환을 제어하고 Pillow 이미지와 Pygame 효과음을 연결했습니다.

문제 생성, 게임 진행, UI, 타이머, 점수, 사운드, 랭킹을 모듈로 분리했습니다. JSON 기록 저장과 Windows 실행 파일 패키징까지 이어가며 하나의 프로그램을 완성하는 과정을 경험했습니다.

설명 기준: 현재 Mygame2/EXE 소스. Mygame2.zip의 기본 진행·점수 규칙을 함께 확인했으며, 방향키 지원·2초 경고·랭킹은 현재 폴더에 추가된 구현입니다.
